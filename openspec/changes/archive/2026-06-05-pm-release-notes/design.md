## Context

The `project-management` skill manages tickets, sprints, and docs across GitHub, GitLab, Jira, and Plane. Teams using a tag-based deployment pipeline need release notes that reflect what changed between two git tags — specifically which tracker tickets were resolved — without manually writing changelogs.

The strategy: `main` always goes to dev, tagging deploys to UAT, and promoting the same tag deploys to PROD. Release notes are generated at tag time and cover only what's new since the previous tag.

## Goals / Non-Goals

**Goals:**
- Extract ticket references from commit messages in the range `prev-tag..current-tag`
- Fetch ticket titles from the configured tracker and group by label
- Apply environment-appropriate framing based on a user qualifier (UAT / PROD / neutral)
- Publish to GitLab Release when provider is GitLab; write to `docs/release_notes/{tag_name}.md` otherwise
- Handle the "first release" case (no previous tag) by ranging from the initial commit

**Non-Goals:**
- Automatic triggering from CI — release notes are generated by manual user invocation only
- DEV environment release notes (no tag = no notes)
- Semantic versioning enforcement or bumping
- CHANGELOG.md management

## Decisions

### D1 — Tag range: always prev-tag..current-tag, no env branching

**Decision**: Release notes always cover the diff between the two most recent semver tags. Environment (UAT/PROD) affects only the framing header, not the content.

**Rationale**: The same tag travels from UAT to PROD — the commits in scope are identical. Generating different content per environment would be misleading. The team runs "release notes for uat" when the tag is cut, then "release notes for prod" when it's promoted; both produce the same ticket list under a different header.

**Alternative considered**: Separate UAT and PROD diff ranges. Rejected — with a tag-based pipeline, the promoted artifact is identical. Different ranges would imply different code, which is wrong.

### D2 — Tag sorting: semver-aware, not lexicographic

**Decision**: Sort tags using semver ordering (`v1.10.0` > `v1.9.0`) when finding the previous tag.

**Rationale**: Lexicographic sort produces wrong results for double-digit minor/patch versions, which is a common failure mode. Semver parsing is the only correct approach.

**Implementation**: Run `git tag --sort=-version:refname` (git's built-in semver sort) filtered to `v*` pattern, then take index [1] as the previous tag when HEAD is on index [0].

### D3 — Publish routing: provider-based, no config required

**Decision**: If `provider.name == "gitlab"` in `.project/config.yaml`, publish to GitLab Release. For all other providers, write `docs/release_notes/{tag_name}.md`.

**Rationale**: GitLab has a first-class Release concept attached to tags. Other providers (GitHub, Jira, Plane) either have different release mechanisms or none. A markdown file in `docs/release_notes/` is universally accessible and version-controlled. No config flag needed — the provider is already known.

**Alternative considered**: `release.publish_to` config key. Rejected — adds configuration overhead for a decision that follows deterministically from the provider.

### D4 — Unlinked commits: include in "Other" group by default

**Decision**: Commits with no ticket reference are collected into an "Other" group showing the raw commit subject line. Default is to include them; suppressed by `release.include_unlinked_commits: false`.

**Rationale**: For QA testers on UAT, unlinked commits (chores, dependency bumps) are useful signal. For PROD-facing changelogs teams may want to suppress them. The default errs toward more information.

### D5 — Ticket extraction: parse standard patterns, no tracker query for disambiguation

**Decision**: Extract ticket IDs from commit messages using these patterns (in priority order):
1. `[A-Z]+-\d+` — Jira/Plane style key (e.g. `PROJ-42`)
2. `#\d+` — GitHub/GitLab style number (e.g. `#42`, `Closes #42`)
3. Full issue URLs — extract the numeric ID from the path

Fetch titles for all extracted IDs via the tracker MCP. Deduplicate by ID (same ticket may appear in multiple commits).

**Non-goal**: Disambiguating bare numbers across multiple repos. Scope is the single configured project.

### D6 — First release fallback: range from initial commit

**Decision**: When no previous tag exists (`git describe` fails on `HEAD^`), use `git rev-list --max-parents=0 HEAD` as the lower bound of the range.

**Rationale**: The initial commit is the natural lower bound for the first release. An empty range would be silently misleading.

## GitLab Release write path

Uses the same write-path resolution pattern as other GitLab writes in the skill:

1. `ToolSearch("mcp__gitlab__create_release")` → MCP path
2. `GITLAB_TOKEN` set → REST API: `POST /api/v4/projects/{id}/releases`
3. Neither → print release notes to terminal with instructions to publish manually

Release body format (GitLab markdown):

```markdown
## {tag_name}

{env_header}

### {Label Group 1} (N tickets)
- TICK-30: Auth token refresh
- TICK-31: Session expiry fix

### {Label Group 2} (N tickets)
- TICK-35: Login form validation

### Other
- chore: bump dependencies
- fix: typo in error message
```

## Markdown file format (non-GitLab)

File path: `docs/release_notes/{tag_name}.md`

Same body as GitLab release. Created fresh per tag (not appended to a single CHANGELOG). Directory is created if absent.

## Environment framing headers

| User qualifier | Header line |
|---|---|
| none | `Release {tag_name}` |
| `for uat` / `uat` | `Release Candidate {tag_name}` |
| `for prod` / `prod` / `production` | `Released {tag_name} to production` |

## Risks / Trade-offs

**[Risk] `git describe` fails when not on a tag** → The skill checks `git describe --exact-match --tags HEAD` first. If the user is not on a tag, emit `⚠ Not on a tag — checkout or create a tag first` and stop. No silent wrong-range generation.

**[Risk] Tracker MCP unavailable for ticket title fetch** → Degrade gracefully: include the ticket ID without a title, label it as "unfetched". Do not block release note generation on MCP failures.

**[Risk] Large number of commits between tags** → Cap ticket fetch at 50 unique IDs. Emit `ℹ {N} ticket references found — showing first 50` if over limit.
